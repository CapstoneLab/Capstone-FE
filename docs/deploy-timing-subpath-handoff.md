## 1. 배포된 서비스에 들어가지지 않음 (필수)

배포 URL: `https://112.186.136.153/services/NekoNyangYee/thkim-resume/`

### 확인한 사실

| 확인 | 결과 |
|---|---|
| `GET .../thkim-resume` | `301` → `/services/NekoNyangYee/thkim-resume/` (정상) |
| `GET .../thkim-resume/` | `200`, index.html 758B, `X-Cicd-Service: nekonyangyee/thkim-resume` |
| JS/CSS (`.../assets/index-*.js`, `.css`) | `200` — Vite `base`가 서비스 경로로 잘 들어가 있음 |
| TLS 인증서 | Let's Encrypt, IP SAN `112.186.136.153`, 유효 (11/19 만료) |
| `GET .../thkim-resume/projects` | **`301` → `http://112.186.136.153/projects/`** ← 문제 |
| `GET /portfolio-mark.svg` (index.html의 favicon) | `404` |

### 원인

1. **앱이 루트 경로(`/`)를 가정합니다.** 번들을 보면 라우팅이 `window.location.pathname`을 그대로 비교합니다
   (`/` = 홈, `/projects/<slug>` = 상세, 그 외 = "페이지를 찾을 수 없음").
   서비스 경로 `/services/NekoNyangYee/thkim-resume/`에서는 pathname이 `/`가 아니므로 **404 화면이 렌더링**되고,
   "포트폴리오로 돌아가기" 링크(`href="/"`)는 서버 루트로 나갑니다.
2. **컨테이너 nginx의 리다이렉트가 서비스 경로와 https를 버립니다.** 경로 접두사를 벗긴 요청을 받은 nginx가
   디렉터리 리다이렉트를 절대 URL `http://112.186.136.153/projects/`로 만듭니다. Caddy가 이를 되돌리지 않습니다.

### 요청

- **(권장) 서비스별 서브도메인 또는 포트로 호스팅**해서 앱이 `/`에서 동작하게 해 주세요. 사용자 앱을 하나하나 고칠 필요가 없어집니다.
- 경로 방식을 유지한다면 서비스 nginx 설정에 다음을 넣어 주세요.
  ```nginx
  absolute_redirect off;            # Location을 상대 경로로
  location / { try_files $uri $uri/ /index.html; }   # SPA 하위 경로 폴백
  ```
  그리고 Caddy에서 `X-Forwarded-Prefix: /services/<owner>/<repo>`를 넘겨 주세요.
- 경로 방식에서는 앱도 `import.meta.env.BASE_URL`(또는 라우터 `basename`)을 써야 합니다.
  배포 화면에 "이 서비스는 `/services/<owner>/<repo>/` 아래에서 실행됩니다" 안내가 필요합니다.

## 2. 배포가 느림 (확인 필요)

스크린샷의 단계별 시간 합계와 전체 시간이 크게 다릅니다.

| 단계 | 시간 |
|---|---|
| 클론 9s · 설치 11s · 경량 5s · 테스트 4s(건너뜀) · 심화 9s · 게이트 4s · 빌드 6s · 배포 9s | **합계 57s** |
| 전체 소요 | **2분 12초 (132s)** |

- **약 75초가 단계 밖에서 쓰입니다.** 큐 대기, 컨테이너 기동, 단계 사이 대기, 결과 집계 등이 후보입니다.
- 배포 파일의 `Last-Modified`는 **23:40:44 (KST)** 입니다. 클론이 23:39:12에 시작했고 전체가 2분 12초라면,
  잡 종료는 23:41:24 무렵입니다. 즉 **파일 배치 후 약 40초 뒤에 잡이 끝납니다.**
  이 수치는 클론 시작을 잡 시작으로 놓고 계산한 추정값입니다.

### 요청

- 잡 `created_at` · `started_at` · 각 단계 `started_at/ended_at` · `completed_at`을 비교해 단계 사이 공백이 어디서 생기는지 확인해 주세요.
- 배포 단계 성공 후 잡 완료까지 무엇을 기다리는지(헬스체크, 결과 저장 등) 확인해 주세요.
- 실행이 끝난 잡의 `duration_secs`가 "현재 시각 − started_at"으로 계속 늘어나지 않는지도 확인 부탁드립니다
  (프론트는 이제 끝난 잡을 `completed_at − started_at`으로 고정합니다).

## 참고: 프론트에서 반영한 것 (v1.7.x)

- **서버 시간 동기화:** 실시간 로그와 엔진 하트비트의 서버 시각으로 PC 시계와의 차이를 추정하고,
  진행 중 단계와 전체 경과 시간을 서버 시계 기준으로 계산합니다.
- **진행률:** 백엔드가 `skipped`로 보고한 단계를 완료로 셉니다(테스트 건너뜀 → 8/8, 100%).
- **끝난 실행의 시간 증가:** 끝난 실행은 서버 타임스탬프로 고정합니다.
  단계가 모두 끝났는데 잡 상태가 아직 바뀌지 않은 경우에도 마지막 단계 종료 시각에서 멈춥니다.
- **중단된 실행:** 단계가 실패·취소되면 잡 상태가 바뀌기 전이라도 그 단계의 `ended_at`에서 시간을 멈춥니다.
  엔진 하트비트와 로그가 60초 넘게 끊기면 마지막 신호 시각에서 멈추고 "엔진 응답 없음"을 표시합니다.
  백엔드는 중단 시 잡 `status`와 `completed_at`을 바로 채워 주세요.
- **전체 시간 = 단계 합 + 대기:** 모든 타이머가 서버 `started_at` 기준 하나의 시계를 씁니다.
  화면에 "2분 12초 (단계 57초 + 대기 1분 15초)"처럼 단계 밖 시간을 따로 보여줍니다.
- **배포 URL 표시:** 잡 완료를 기다리지 않고 배포 단계 성공 즉시 `GET /api/pipelines/{id}/deployment`를 조회합니다.
