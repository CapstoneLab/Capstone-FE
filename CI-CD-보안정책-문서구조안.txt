신규 CI/CD 보안정책 문서 구조안
================================

목적
----
기존 보안정책 초안을 정책, 기술 표준, 운영 절차, 감사 부록으로 분리한다.
내용을 축소하는 것이 아니라, 변경 빈도와 사용 목적에 따라 문서 책임을 나누는 것을 목표로 한다.


1. CI/CD 보안정책
=================

1.1 목적 및 적용범위
--------------------
- 신규 CI/CD 프로그램
- 소스코드, 빌드, 테스트, 릴리스, 배포
- 개발·시험·운영 환경
- 내부 시스템과 외부 협력사 적용 여부

1.2 보안 원칙
-------------
- 최소권한
- 개발·시험·운영 환경 분리
- 승인된 코드와 아티팩트만 배포
- 필수 보안검사 실패 시 자동 통과 금지
- 활성 Secret, 악성코드, 변조 아티팩트는 예외 없이 차단
- 검사된 커밋과 배포 아티팩트의 일치성 검증

1.3 역할과 책임
---------------
- 정책 소유자
- 정보보호 책임자
- 개발팀
- 운영팀
- CI/CD 플랫폼 관리자
- 서비스 소유자
- 예외 승인권자
- 사고대응 담당자

1.4 위험 분류 원칙
------------------
- CVSS는 기술적 심각도를 표현한다.
- P0~P4는 조직의 배포 위험도를 표현한다.
- 실제 악용, 인터넷 노출, 자산 중요도, 보완통제를 추가로 반영한다.
- CVSS가 없는 Secret, 무결성 오류, 설정 오류도 별도로 평가한다.

1.5 필수 보안통제
-----------------
- 계정·권한관리
- 소스코드 변경 승인
- Secret 탐지
- SAST
- SCA
- IaC 검사
- 컨테이너 검사
- SBOM 및 아티팩트 서명
- 배포 승인
- 감사로그
- 취약점 조치와 예외관리

1.6 배포 차단 원칙
------------------
- P0: 침해 진행, 활성 Secret, 악성 행위, 심각한 무결성 훼손.
  즉시 격리·차단·사고대응한다.
- P1: 검증된 고위험 공격경로 또는 중요 자산의 High/Critical 취약점.
  병합·릴리스·배포를 차단한다.
- P2: 제한적이지만 유의미한 위험.
  승인, 담당자, 조치기한이 등록된 경우 조건부 진행한다.
- P3: 낮은 위험.
  이슈 등록 및 개선기한을 관리한다.
- P4: 정보성 또는 권고사항.
  기록하고 정기적으로 검토한다.
- 활성 Secret, 악성 실행, 아티팩트 무결성 실패, 권한 우회,
  필수 검사 실패는 위험 수용으로 우회할 수 없다.

1.7 예외 및 긴급배포 원칙
-------------------------
- 예외 승인권자
- 승인 사유
- 대상 커밋과 아티팩트
- 보완통제
- 만료일
- 사후 검증
- Break-glass 사용 조건

취약점을 무시하는 위험 수용과, 취약점 해결을 위한 긴급 배포 승인은
서로 다른 절차로 관리한다.

1.8 감사 및 위반관리
--------------------
- 증빙 보관
- 로그 무결성
- 정기 검토
- 정책 위반 보고
- 예외 만료 검토


2. CI/CD 보안운영 표준
======================

2.1 단계별 보안 게이트
----------------------

[Gate A: Push/PR]
- Secret 탐지
- SAST
- 금지 패턴 검사
- 신뢰할 수 없는 PR에 운영 Secret 제공 금지

[Gate B: Merge]
- 필수 검사 성공
- 코드 리뷰
- 보호 브랜치
- 정책 파일 별도 승인
- 승인 후 커밋 변경 시 재검사

[Gate C: Build/Release]
- SCA
- 이미지 검사
- IaC 검사
- SBOM 생성
- provenance 생성
- 아티팩트 서명 및 digest 검증

[Gate D: Stage]
- DAST
- API 인증·인가 테스트
- 중요 기능 보안 테스트

[Gate E: Production Deploy]
- commit SHA와 artifact digest 일치 확인
- 승인자와 배포자 권한 확인
- 정책 버전 확인
- 예외 만료 여부 확인

[Gate F: Post-deploy]
- 신규 CVE 재평가
- 신규 P0/P1 알림
- 수정 후 재검사
- 필요 시 롤백 또는 격리

2.2 P0~P4 상세 기준
--------------------

P0: 침해 진행, 활성 Secret, 악성 행위, 심각한 무결성 훼손
     즉시 격리·차단·사고대응

P1: 검증된 고위험 공격경로 또는 중요 자산의 High/Critical 취약점
     병합·릴리스·배포 차단

P2: 제한적이지만 유의미한 위험
     승인과 기한 등록 후 조건부 진행

P3: 낮은 위험
     이슈 등록 및 개선

P4: 정보성·권고사항
     기록 및 정기 검토

CVSS는 P등급을 자동 결정하는 유일한 기준이 아니다.
실제 악용, 자산 중요도, 인터넷 노출, 공격경로, 보완통제를 함께 평가한다.

2.3 누적 취약점 기준
--------------------
- 신규 고유 취약점의 정의
- 중복 제거 기준
- 신규·기존 취약점 분리
- Medium/P2 1~4건, 5~9건, 10~29건, 30건 이상 기준
- 공격경로 연계 시 등급 상향
- 릴리스 단위 누적 집계
- PR 분할 우회 방지

권장 기본값:
- 1~4건: 경고, 이슈 등록, 담당자·기한 지정
- 5~9건: 강화 경고, 개선계획 필수
- 10~29건: 수동 검토 및 승인 전까지 배포 보류
- 30건 이상: 기본 배포 차단

30건 기준은 공식 표준이 아닌 조직 자체 운영 기준이며,
파일럿 결과에 따라 변경 가능한 정책 변수로 관리한다.

2.4 필수 데이터 필드
---------------------
- finding_id
- scanner
- rule_id
- commit_sha
- pipeline_id
- artifact_digest
- CVE/CWE
- CVSS 버전·벡터·점수
- asset_criticality
- exposure
- exploit_evidence
- final_risk_tier
- gate_decision
- policy_version
- evidence_uri
- exception_expiry
- remediation_due

2.5 공급망 보안 기준
--------------------
- Runner 격리
- Fork PR Secret 제한
- 패키지 저장소 allowlist
- 빌드 네트워크 통제
- 캐시 오염 방지
- OIDC 권한 제한
- 서명키 관리
- SBOM 포맷
- provenance 검증
- 아티팩트 보존기간


3. CI/CD 보안운영 절차서
========================

3.1 일반 취약점 발견
--------------------
1. 스캔 완료
2. 결과 정규화
3. 오탐 여부 확인
4. CVSS와 최종 위험도 산정
5. 담당자·기한 등록
6. 게이트 판정
7. 조치 후 재검사

3.2 Secret 노출
---------------
1. PR·배포 중단
2. Secret 유효성 확인
3. 즉시 폐기·회전
4. 사용 흔적 확인
5. 관련 로그 및 아티팩트 조사
6. 재탐지
7. 사고 여부 판단

Secret 원문은 감사로그에 저장하지 않는다.

3.3 악성코드 또는 데이터 반출
-----------------------------
1. 해당 Job 중단
2. Runner 격리
3. 아티팩트 격리
4. 자격증명 폐기
5. 사고대응 절차 시작
6. 증거 보존
7. 승인된 환경에서 재빌드

3.4 스캐너 장애
---------------
1. SCAN_ERROR 기록
2. 제한된 횟수만 자동 재시도
3. 계속 실패하면 배포 보류
4. 담당자 통보
5. 긴급배포 필요성 평가
6. 승인된 Break-glass 적용 여부 결정
7. 사후 전체 재검사

3.5 긴급배포
------------
- 긴급 사유
- 승인자 2인
- 배포 대상과 범위
- 사용한 보완통제
- 모니터링 계획
- 사후 재검사 기한
- 결과 보고

3.6 재개 및 종료
----------------
- BLOCK: 수정 커밋 생성 후 전체 재검사
- SECURITY_HOLD: 사고조사와 자격증명 재설정 후 재개
- SCAN_ERROR: 동일 조건의 필수 검사 성공 후 재개
- MANUAL_REVIEW: 승인자와 적용 범위 기록 후 재개


4. CI/CD 보안검증 및 감사 부록
==============================

4.1 수용 테스트
---------------
- P1 취약점 병합 차단
- 활성 Secret 배포 차단
- 필수 스캐너 실패 시 PASS 금지
- 이전 커밋 검사 결과 재사용 방지
- 서명·digest 불일치 차단
- P2 조건부 허용
- 오탐 승인 범위 제한
- PR 분할을 통한 누적 기준 우회 방지
- 예외 만료 후 자동 재평가

4.2 정책 엔진 의사코드
----------------------
정책 본문에는 원칙만 두고, 상세 의사코드는 부록에 둔다.

function evaluateGate(event, findings, scan, context, artifact):
    if confirmedMaliciousExecution(event):
        stopJob()
        quarantineRunnerAndArtifacts()
        notifySecurity()
        return SECURITY_HOLD

    if confirmedSecretExposure(findings):
        revokeAndRotateSecret()
        notifySecurity()
        return SECURITY_HOLD

    if artifactIntegrityInvalid(artifact, context):
        quarantineArtifact()
        return BLOCK

    if mandatoryChecksFailed(scan):
        return SCAN_ERROR

    risk = assessRisk(findings, context)

    if risk.hasP0OrP1:
        return BLOCK

    if risk.hasP2:
        if validTrackingAndApproval(context):
            return ALLOW_WITH_TRACKING
        return MANUAL_REVIEW

    return ALLOW

4.3 감사 증빙
-------------
- 자산관리대장
- 위험평가서
- 코드리뷰 기록
- 스캔 원본 결과
- SBOM
- provenance
- 서명·digest 검증 결과
- 배포 승인 기록
- 예외 승인서
- 재검사 결과
- 사고대응 기록

4.4 점검 체크리스트
-------------------
- PR 생성 시 필수 스캐너가 실행되는가?
- 스캐너 실패가 PASS로 처리되지 않는가?
- CVSS와 내부 P등급이 별도로 저장되는가?
- Secret·설정·무결성 오류도 분류되는가?
- P0/P1 병합 및 배포 차단이 작동하는가?
- P2 조건부 허용에 담당자·기한·승인 근거가 있는가?
- 운영 배포가 검사된 커밋과 서명된 아티팩트에 연결되는가?
- 예외 만료와 신규 위험 공개 시 재평가되는가?
- 취약점 조치 후 재검사하는가?

4.5 표준 매핑표
---------------

통제: 코드 검토
참고 기준: NIST SSDF PW.7
조직 적용: PR 리뷰·보호 브랜치
증빙: 리뷰 기록

통제: 보안시험
참고 기준: NIST SSDF PW.8
조직 적용: SAST·DAST
증빙: 검사 결과

통제: 공급망 보호
참고 기준: NIST SP 800-204D
조직 적용: SBOM·서명·provenance
증빙: 검증 로그

통제: 위험평가
참고 기준: ISMS-P 1.2.3
조직 적용: P0~P4 분류
증빙: 위험평가서

통제: 취약점 조치
참고 기준: ISMS-P 2.11.2
조직 적용: SLA·재검사
증빙: 조치대장

통제: 공격 시나리오
참고 기준: MITRE ATT&CK
조직 적용: 위협 모델링
증빙: 공격경로 분석


5. 기존 장의 이동표
====================

제1장 적용 기준과 역할
-> 보안정책

제2장 CI/CD 운영 프로세스
-> 보안정책 + 보안운영 표준

제3장 CVSS 및 배포통제
-> 보안정책 + 보안운영 표준

제4장 SEC-01~SEC-12
-> 보안정책의 필수 통제 목록

제5장 표준 수용 방법
-> 보안정책 또는 표준 매핑 부록

제6장 ISMS-P 체크리스트
-> 감사 부록

제7장 정책 엔진 데이터 필드
-> 보안운영 표준

제8장 최종 결론
-> 보안정책 요약

제9장 공식 참고자료
-> 각 문서의 참고자료 부록

제10장 취약점 자동 대응
-> 보안운영 표준 + 운영절차서

제11장 Stop 정책
-> 운영절차서

제12장 SEC-13 누적 정책
-> 보안운영 표준

의사코드 및 수용 테스트
-> 감사 부록


최종 원칙
==========

상위 정책에는 조직이 반드시 지켜야 하는 안정적인 원칙을 둔다.
보안운영 표준에는 시스템 구현에 필요한 기준과 조정 가능한 임계값을 둔다.
운영절차서에는 장애, 사고, 긴급배포, 재개 절차를 둔다.
감사 부록에는 의사코드, 테스트, 체크리스트, 증빙 필드를 둔다.

이 구조를 사용하면 현재 문서의 상세함은 유지하면서도
정책 승인, 시스템 구현, 운영 대응, 감사 준비를 각각 쉽게 수행할 수 있다.
